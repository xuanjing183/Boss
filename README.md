# BOSS 直聘 · 收藏岗位大模型打招呼助手

一个油猴（Tampermonkey）脚本：**读取你在 BOSS 直聘网页版收藏的岗位，结合本地简历，让大模型写出个性化的打招呼语，再半自动 / 全自动发给 HR。**

单文件、无构建、无后端。简历、岗位、草稿、API Key 都只存在本机 Tampermonkey 的存储里。

> 当前版本 **v0.5.9**。界面与文档均为中文，目标站点是 BOSS 直聘网页版（zhipin.com）。

```
收藏/感兴趣列表 ──「抓当前页」──> 岗位库（新抓的默认不勾选）
                                    │ 勾选 = 进队列；缺 JD 就后台开详情页抓回来
                                    ▼
                    简历(PDF/文本) + JD + 提示词 ──> 大模型（可多模型并行）──> 打招呼语草稿
                                                                                 │
              发送：后台打开列表页 → 点这条岗位卡片自己的「继续沟通/立即沟通」 → 沟通页
                              （卡片找不到 / 没有按钮 → 自动退回岗位详情页入口）
                                                                                 │
                                    半自动：填进输入框，由你按 Enter 或点「发送」
                                    全自动：确认会话身份后填 + 点「发送」
```

---

## 先读这个：风险与合规

- **批量自动打招呼违反 BOSS 直聘用户协议**，可能触发限流、功能封禁甚至账号封禁。脚本默认是**半自动**，默认**每日上限 20 条、发送间隔 9–22 秒随机**。先用这套保守值小规模验证，别一上来就全自动跑几十条。
- 脚本在发送前会核对「当前会话就是这条岗位」：拿导航记录里的 `jobId`、右侧职位名做证据。对不上就停手；实在拿不到证据就只填不发，留给你确认。这是为了降低发错人的概率，不是绝对保证。
- API Key 会随请求发给你自己配置的大模型服务商；岗位文本和简历也会进入提示词。用你自己的 Key，**不要提交到公开仓库**。
- 本项目仅供学习交流。使用它产生的账号、法律与社交后果由使用者自行承担。

## 安装

**方式 A（推荐）**：浏览器打开仓库里的 [`boss-zhipin-llm-greet.user.js`](./boss-zhipin-llm-greet.user.js)（或 Raw 地址），Tampermonkey 识别 `.user.js` 后会弹出安装页，点「安装」。

**方式 B（手动粘贴）**：

1. Edge / Chrome 应用商店安装 **Tampermonkey**。
2. Edge 额外确认：`edge://extensions` → Tampermonkey「详细信息」→ 打开 **允许用户脚本**。
3. Tampermonkey 点「添加新脚本」，把整份 `.user.js` 粘进去，`Ctrl+S`。

装好后打开任意 BOSS 页面，右下角出现 **「打招呼助手」** 悬浮按钮；`Alt+P` 显示 / 隐藏面板。油猴菜单里还有「打开/显示助手面板」和「重置全部本地数据」。

## 首次使用

1. **设置 → 大模型接口**：填 API Base / API Key / Model，点「连通测试」，日志出现模型回执再继续。想多模型并行，就展开下面的「多模型并行」逐组添加（见[多模型并行](#多模型并行v057--v058)）。
2. **简历**：选一份 PDF 自动抽取，或直接粘贴正文 →「保存文本」。
3. 打开 BOSS 的**收藏/感兴趣列表页**，把页面滚到底让懒加载出完，回面板 **岗位 → 抓当前页**（或「自动翻页抓」）。
4. **勾选要处理的岗位**。新抓到的岗位默认一条都不勾（v0.5.1 起）：收藏列表里常躺着大量早已不打算发的岗位，全塞进队列意味着全都要开后台标签抓 JD。勾上哪条才处理哪条。
5. 勾上的岗位若还没有 JD，脚本会**攒成一批**在后台打开详情页抓回来（防抖 1.5 秒），抓完自动关标签。标题栏「详情 N」上涨就是抓到了。
6. **队列**：半自动下点「生成」→ 审草稿 → 点「发送」；全自动下按钮叫「生成并发送」，点一次跑完整条链路。点「开始批量」时，生成会交给脚本自己开的**后台「生成器」标签页**跑，你切页面、翻页、关面板都不打断生成。

> **没抓到 JD 的岗位不会生成招呼语**（v0.4.3 起的硬规矩）：脚本不会拿列表卡片那一行凑合写，队列里那行的按钮会变成「补抓详情并生成」。

## 岗位详情（JD）是怎么拿到的

**脚本不在列表页点任何按钮，而是把卡片标题那个链接放到后台标签里打开。**

```
「抓当前页」收集 a[href*="job_detail"] / a[href*="jobDetail"] / a[href*="/job/"] → 存进 jobs（含 url，默认不勾选）
        ↓ 勾选 = 进队列（连点几颗并成一批）
fetchDetails() 逐个 GM_openInTab(job.url, {active:false})
        ↓ 后台标签认出「我是来抓详情的」（URL 命中 pendingDetails）
scrapeDetail() 取详情页正文容器 → 写进 GM 存储 details[jobId]
        ↓
面板每 2 秒读存储，把 JD 合并回队列；用完自动关闭该标签
```

有 JD 时提示词里给的是详情页正文；薪资、地点等正文没有的字段仍从卡片带上，两份岗位描述不会互相打架。

### 没抓到 JD 就不生成

生成前 `generateOne()` 会先并回存储里的最新 JD，确认 `hasDetail(id)`；**没有就直接抛错，一个模型请求都不发**。这条判据只写在 `generateOne()` 一处，批量和队列 UI 只负责把结果翻译成看得懂的标记，避免两边判断走岔。

| 位置 | 看到什么 | 怎么办 |
| --- | --- | --- |
| 队列 | 按钮是「补抓详情并生成」 | 点一下先捞 JD 再写；还抓不到会明说 |
| 岗位 | 行标「缺 JD 不生成」 | 勾选后点「抓选中岗位详情」 |
| 批量 | 该条标「缺 JD 已跳过」，日志写原因 | 批量开始前会先统一补一轮 JD；跳过的不占发送间隔 |
| 日志 | `详情抓取结束，还差 N 个没抓到` | 按名字自己补，或进页面看岗位描述 |

**卡片没有详情页链接**的岗位抓不到 JD，只能你自己进页面看。**详情页被登录墙挡住或没加载完**时 JD 会是 0，日志里的「详情回收进度」不动就是这种情况。

JD 正文参与草稿指纹，所以补抓到 / 更新 JD 会让旧草稿自动变成「草稿已过期」，发送按钮禁用。

## 发送

### 两种模式

**半自动（默认）**：脚本负责生成草稿并把话**填进聊天输入框**，最后一下由你按 `Enter` 或点站点「发送」。

- 你当前就在沟通页：当场填好。
- 当前不在沟通页：脚本另开标签页走到这条岗位的沟通页，**只填不发**，队列标成「已填待确认」。
- 它绝不会在你正看着的页面上点岗位卡片的「立即沟通」。

**全自动**：生成、走到沟通页、填、点发送全部由脚本在后台标签里完成。队列里的单条按钮也叫「生成并发送」，点一次不用再点第二下。每日上限（默认 20）在自动发送前拦：批量到顶就停；单条到顶则草稿照生成、但不碰沟通页、不计数；半自动不拦（最后一下是你点）。

### 两个发送入口

| 入口 | 怎么走 | 何时使用 |
| --- | --- | --- |
| **列表卡片入口**（默认，`sendViaList`） | 另开一个列表页标签 → 滚动找这条岗位的卡片 → 悬停 → 点卡片右上角的「继续沟通/立即沟通」→ 一步到沟通页 | 少开一次详情页，通常更快 |
| **岗位详情页入口** | 另开岗位详情页 → 找沟通入口（`a.btn-startchat`）→ 点它 → 到沟通页 | 关掉列表入口时；也是列表入口明确走不通时的自动退路 |

退回只发生在「这一趟一个字都没发出去」时：卡片找不到、卡片上没按钮、或这条岗位没记下列表页地址（v0.5.0 之前抓的老数据）；**所以不会把同一条发两遍**。如果按钮的 `redirect-url` 里 `jobId` 对不上，或会话身份明确指向别的岗位，脚本只停手、不换入口重试。

脚本只在**它自己开出来的**后台标签里点卡片按钮，绝不在你正在看的那一页点。认领条件同时成立才放行：页面加载时判一次（不轮询）、地址或导航记录里带 `#bgSend=<岗位id>` 标记、这一页比请求新、请求尚未被别的标签认领。缺一条就只是普通页面。

### 会话身份与成功信号

沟通页会把地址栏洗成 `https://www.zhipin.com/web/geek/chat`，query 全没了，整页也没有 `a[href*="job_detail"]`。脚本用的是两档证据：`performance.getEntriesByType('navigation')[0].name` 里那一跳的 `jobId` / `securityId`，以及右侧 `span.position-name` 的职位名（必须限定在右半侧，左侧会话列表里会出现别的岗位名）。

- `yes`：证据对得上 → 填并发送；
- `unknown`：拿不到可比对证据 → **只填不发**，标「已填待确认」；
- `no`：证据明确指向另一个岗位 → **一个字都不填**。

**成功唯一判据是「输入框被清空」**。输入框里的话本来就在页面正文里，所以「正文出现这句话」不能当成功；旧版因此会把没发出去误报成成功。

### v0.5.9：发送按钮兼容真实站点

用户实测日志里，最基础的发送全线失败：`找到了输入框但没找到「发送」按钮，也没能用回车发出去`。在已登录的真实页面上核对后发现：BOSS 这组操作按钮已经是 `<div class="btn-v2 btn-sure-v2 …">`，**不是 `<button>`**，也没有 `btn-send` 类。（实测到的是同组件的会话列表搜索按钮；沟通页那颗在点开会话后调试器会断开，没能直接抓到，所以代码里仍同时保留 `button` / `[role=button]` / `[class*=send]` 几条老路径。）

现在的 `findSendButton()`：

- 候选范围扩大到 `button, [role="button"], .btn-v2, .btn-sure-v2, [class*="send"]`；
- 文案仍**精确等于「发送」**，避免误抓搜索框；
- 若站点把文案改成「提交」，只认右侧沟通面板里的那颗（`left >= innerWidth * 0.28`），左侧会话列表顶部的搜索框也叫「提交」；
- 先等按钮出现（最多 20 × 250ms），再等它摘掉 `disabled`（`disabled` 在空输入时是 **class**，不是属性），等不到也点一下，最终仍以输入框是否清空为准；
- 仍然排除任何上传 / 表情 / 图片控件（`isUploadish`），不会弹出系统选图框。

回归 fixture 已改成真实的 `<div class="btn-v2 btn-sure-v2">`。把选择器退回旧写法，立刻有 16 条断言变红；恢复后 257 条闭环断言全绿。

## 大模型接入

任何 OpenAI 兼容的 `/chat/completions` 都能用。脚本用 `GM_xmlhttpRequest` 直连，绕过 CORS，所以需要 `@connect *`；首次保存后如被询问授权，同意即可。**API Base 不要带 `/chat/completions`**，脚本会自己拼。

| 服务商 | API Base | Model 示例 |
| --- | --- | --- |
| DeepSeek（默认） | `https://api.deepseek.com/v1` | `deepseek-chat` |
| Moonshot / Kimi | `https://api.moonshot.cn/v1` | `moonshot-v1-8k` |
| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-flash` |
| 阿里云百炼（通义） | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| 火山方舟 | `https://ark.cn-beijing.volces.com/api/v3` | `ep-xxxxxxxx`（接入点 ID） |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |
| 自建 / 内网网关 | 按网关地址填，通常末尾带 `/v1` | 网关暴露的模型名 |

默认 System 提示词：第一句直接说你是谁、能做什么；从简历里挑 2–3 条与 JD 最匹配的经历，不编造；60–120 字单段落，像真人打字；不用 markdown、不加 emoji；不出现薪资期望和「贵公司」。

**简历、岗位信息（含 JD）、系统/用户提示词、模型名、温度**任一变化，旧草稿都会自动标记「草稿已过期」，批量时重新生成，避免把按旧简历写的话发给新 HR。

### 多模型并行（v0.5.7 / v0.5.8）

设置页的「大模型接口」里有一个可折叠的 **「多模型并行（点击展开）」**。展开后是若干张卡片，每张卡片和上面的单模型表单格式一致：`API Base` / `API Key` / `Model`，卡片标题就是内部标签 `m1`、`m2`……，标题右侧有「删除」。底部是「+ 添加模型」和「保存多模型配置」。

使用方式：

1. 展开「多模型并行」，点「+ 添加模型」，逐张填好 Key 和 Model；
2. 点「保存多模型配置」。**只保留 Key 和 Model 都填了的卡片**，空行会被丢弃；
3. 把模型全部删除并保存后，刷新页面会按上面那组单 Key 配置自动补一条 `m1`（单 Key 没填就仍然用不了）；当前页面这一轮请至少保留一个模型；
4. 老版本升级时不需要手动迁移：原来的单 Key 配置会自动变成 `m1`。

批量时脚本按**岗位 id 的哈希取模**把岗位分给各个模型，同一条岗位重跑时永远分到同一个模型，草稿指纹不会因为换模型而漂移。每个模型拿到自己的子队列，**各自**开 `min(子队列长度, 并发生成数)` 条 promise 链 worker，互不干扰。因此：

- **总并发上限 ≈ 模型数 × 并发生成数**。例如 3 个模型、并发生成数 3，最多同时有 9 条模型请求在飞；
- 服务商侧是按**每个 Key / 每个模型**分别限额的。报 429 时，先把并发生成数调小；多模型下总额度比单模型高，但仍然受每家服务商自己的限制；
- 半自动下生成器只生成、不发；全自动下发送仍由单一消费者**逐条排队**，间隔照旧。

日志会写清分配结果：

```
· 本轮 20 个岗位，3 个模型并行（并发生成 3 路；发送仍逐条排队，间隔 9~22 秒）
  [m1] qwen-plus → 7 条岗位
  [m2] deepseek-chat → 6 条岗位
  [m3] glm-4-flash → 7 条岗位
→ [m2] 发出模型请求「Java 后端开发」（同时在飞 4 条）
```

### 并发实测探针（v0.5.6）

每轮批量结束，日志会按实际 HTTP 起止时间算一段：

```
· 本轮生成实测：20 次请求，墙上 245.0s，累计 1123.9s，峰值同时在飞 8 条，实际并发度 4.6
  [m1] qwen3.7-max：7 次，墙上 202.0s，累计 780.0s，峰值 3，实际并发度 3.9
```

- **峰值**说明「并发池真的同时挂出了几条请求」；
- **实际并发度** = 累计请求耗时 ÷ 墙上时间，反映平均有几条在同时跑。它通常低于峰值，因为总会有先跑完、后起跑的空档。

用户真机实测过一组：设置 8 路，峰值确实是 8，但实际并发度只有 4.6；单条模型请求延迟在 **34–202 秒**，瓶颈是大模型推理时间，不是 Key 限流。**想再快，换不同模型并行比给同一个模型配多个 Key 更有效。**

### 并发与发送的顺序

- 发送顺序 = **草稿完成顺序**，不再等于岗位列表顺序。想完全按列表顺序，把并发生成数设为 1。
- 服务商报 429 / 5xx 会退避重试，带 0–1.2 秒随机抖动，避免 N 路同时撞墙；日志会提示调小并发。
- 同一条岗位被两路同时处理时有两道闩：`genBusy` 把并发请求合流成一条（不重复烧 token），`sendBusy` 只允许一路在发（同一个 HR 不会收到两遍）。
- 跨标签发送协议只有一个 `sendReq` 存储位，两条发送同时在飞会互相盖掉请求和回执，所以**发送永远不并发**。

## 批量执行：后台生成器、续跑与多标签

### 生成跑在脚本自己的「生成器」标签页（v0.5.5）

生成招呼语只需要三样东西：存储里的简历、存储里的 JD、一次模型请求，完全不需要 DOM。所以从 v0.5.5 起，点「开始批量」会：

1. 往存储写一张交接单 `bgExec = {token, ts, ids, claimed}`；
2. `GM_openInTab(当前页地址#bgExec=<token>)` 开一个后台标签，标题写着 **「招呼语生成器 · 请别关这个标签页」**；
3. 那一页 `boot()` 最优先认领：标记对得上 token，且这一页比交接单新（`performance.timeOrigin >= ts - 1500`）；站点洗掉 hash 时还会从导航记录里找标记；
4. 认领分三步：看有没有别人在跑 → 写下自己的心跳 → 睡 250–700ms 读回来确认还是自己。落选的那一页直接收工；
5. 跑完撤计划并自己关闭（受 `autoCloseDetail` 管）。

因此：

- **你切岗位、翻页、关面板都不会打断生成**，页面也不再弹「是否离开网站？」。`beforeunload` 只在真正执行这一轮的那一页上武装；
- 面板变成观众：「生成中」「剩 X/Y 条」从存储里的 `p.gen` 读；「暂停 / 停止」是往计划里写 `p.pause` / `p.stop`，由执行者在心跳里认；
- 面板日志和生成器日志是**两个独立的键**（`bgLogBuf` / `bgLogExec`），两边不互相覆盖；
- 生成阶段是 N 条 promise 链 worker，**不依赖定时器**。后台隐藏页的 `setInterval` 会被浏览器压到一秒甚至一分钟一次，而模型回包是网络回调，不受影响；
- 代价：全自动下，隐藏页里每条之间的发送间隔、等回执的轮询也可能被压慢；把生成器标签页切到前台会恢复。

**兜底**：没有 `GM_openInTab`、开标签失败、或 25 秒内没人认领（登录墙、验证码、油猴未注入），这一轮会**当场退回你正看着的这一页**跑完，日志说明原因。生成器中途被关掉，心跳断约 15 秒后，别的页面会再派一个接着跑（`p.respawn` 30 秒去重）；已发出的靠持久凭证跳过。

### 整页跳转不丢任务（v0.5.3）

上述生成器是主路径。关掉 `bgExecutor`、或交接失败退回本页时，靠落盘续跑兜底：

- 每轮开始把「要跑哪几条」写进 `bgBatch`（带 `day`，隔夜计划作废），跑着时每 2 秒续心跳；
- 新页面认出没跑完的计划：队列页出现「继续上次批量（剩 N 条）」，`autoResume` 开着则自动接手，但**必须等上一份心跳断掉约 15 秒**，避免和还开着的另一页抢；
- 用户自己按「停止批量」会把计划标成没人认领，任何页面都不自动接着跑；
- 日志副本 `bgLogBuf` 节流写入，新页面接回最近 200 行，并注明「上面 N 行是上一页留下的」。

### 「这条真的发出去了」是持久凭证

确认输入框被清空的那一瞬间，由看见这件事的那个标签页写 `bgSent:<岗位id>`。面板草稿上的「已发送」与它是两回事：面板那一页要是正好在标记前被跳转销毁，续跑时认的是凭证 —— 补记成已发送、吃一次今日额度、**不再碰沟通页**，日志写「这一条在上一页就已经发出去了」。

凭证必须和草稿同生同死：岗位页「清空列表」和油猴菜单「重置全部本地数据」会按前缀一起扫掉 `bgSent:` / 旧协议的 `sendDone:`。否则重抓同一批岗位后，草稿没了凭证还在，点发送会被永远拦住。

### 多个标签页同时活着（v0.5.4）

存储里的 `drafts`、`jobs`、`stats`、`details`、`pendingDetails` 各是一整块，而每个标签页 boot 时读走自己的内存快照。旧写法「改完把整块盖回去」会让一个开了很久、快照很老的页面把别人刚写的记录整块抹掉。

现在两条规矩：

- **只盖自己动过的那一条**：`saveDrafts(ids)` 只替换/删除这几个 id；`saveJobs()` 按 id 取并集；`saveStats()` 同一天取较大值；`saveDetails()` 只并自己认识的 id 且时间戳不旧于存储；`addPending()` / `consumePending()` 只排自己的账、只销自己的账。
- **动手之前先对账**：`syncFromStorage()` 在 3 秒轮询、`runBatch` 进门、发送前、点「继续上次批量」时各执行一次；正在飞的那几条（`genBusy` / `sendBusy`）不许被存储覆盖。

仍然整块覆盖的只有三处，都是故意的：岗位页「清空列表」、油猴菜单「重置全部本地数据」、日志页「重置今日计数」。重置计数会额外写 `stats.resetAt` 时间戳，比它旧的快照不许把 `sent` 抬回来。

**换日归零**：`today()` 按 UTC（北京时间早上 8 点翻），换日时 `sent` / `generated` 归零；boot 时和每 3 秒对账时都会滚一次，页面从昨晚一直开着也会自己翻到新的一天。

## PDF 简历解析

浏览器沙箱读不了磁盘，所以每次都要手动选文件（`.pdf` / `.txt` / `.md`）。PDF 走 pdf.js 3.11.174，默认从 npmmirror（阿里）加载，因为 jsdelivr / unpkg 在大陆经常超时。依次尝试三条路线，单条超时 25 秒自动换下一条：

1. **主线程 fake worker**（最稳，排第一）；
2. **同源 blob worker**：用 `GM_xmlhttpRequest` 取回 worker 源码打成 blob，绕过站点 CSP，且不需要 `eval`；
3. **远程 workerSrc**：要求站点放行镜像域名，失败得很快。

三条都不通时，日志会写明试过哪几条、卡在哪，并提示：**把简历另存为 `.txt` 再选一次，或直接粘贴文本点「保存文本」**。

若镜像在你的网络下也不通，把文件头 `@require` 和设置里的 `pdfWorkerSrc` 一起换成：

```
https://cdn.bootcdn.net/ajax/libs/pdf.js/3.11.174/pdf.min.js
https://cdnjs.cloudflare.com/ajax/libs/pdf.js/3.11.174/pdf.min.js
https://cdn.staticfile.net/pdf.js/3.11.174/pdf.min.js
```

## 常见问题

**「抓当前页」后队列是空的？**
正常。v0.5.1 起新抓到的岗位默认不勾选，勾上才进队列、才自动抓 JD。想全选，用岗位页的「全选/取消」。

**标题栏「详情」一直是 0？**
先确认岗位已勾选。再查日志：有没有「打开 N 个后台标签抓详情」和「详情回收进度 1/N」。一直 0/N 通常是详情页被登录墙挡住、没加载完，或这条岗位没有详情页链接。别把那一批后台标签秒关。

**队列里只有「补抓详情并生成」？**
说明 JD 还没到手。点它先捞 JD 再写；日志接着显示「JD 还是没抓到」的话，通常是详情页没加载出来、被登录墙挡住，或岗位没有详情页链接。

**选了全自动，为什么还要我点「发送」？**
v0.5.1 起不用了：全自动下按钮写着「生成并发送」。如果只看到「生成」，说明当前是半自动（队列页顶部有模式标签），或者面板还是旧版本。它只会在两种情况下停在没发：到了今日上限，或 JD 还没回来。

**发送日志写「找到了输入框但没找到『发送』按钮」，或后台标签 60 秒没回执？**
先看日志走的是哪个入口。v0.5.9 已按真实站点把候选范围扩到 `div.btn-v2.btn-sure-v2` 并保留精确文案「发送」；如果仍失败，按 F12 看一下沟通页那颗按钮的真实标签/文案，再对照「关键选择器」。列表入口超时则先看日志有没有「列表入口没走通…」，再看后台标签停在列表页还是已经跳到沟通页。

**日志先出现「列表入口没走通，退回岗位详情页入口」，会发两遍吗？**
不会。这句只在一条字节都没发出去时出现，退回后才真的发一次，队列只计一次。若是会话身份明确对不上，脚本只停手、不换入口重试。

**脚本会不会在我正看的列表页上点「立即沟通」？**
不会。它只在自己 `GM_openInTab` 开的页面点；认领在加载时判一次，之后不轮询；还要「带 `#bgSend` 标记」且「页面比请求新」两个条件同时成立。四种反例都有独立回归 case。

**批量太慢？**
慢在等模型回话。把并发生成数调到 3–8，或配置多个不同模型并行；发送间隔是给 BOSS 看的，不要为了快把它调得很小。实测单条模型延迟可能 30–200 秒，先看日志的「本轮生成实测」再决定加并发还是换模型。

**日志出现「模型限流/异常 429，X 秒后重试」？**
把并发生成数调回 1–2。退避重试已带随机抖动；偶尔一两条会自动恢复，一直报就是超过服务商给这个 Key 的额度。

**发送顺序和勾选顺序不一样？**
正常。发送顺序 = 草稿完成顺序。想严格按列表顺序，把并发生成数设为 1。

**批量跑到一半切页面会断吗？**
v0.5.5 起默认不断，也不再弹「是否离开网站？」。生成器标签页在跑；面板只显示进度。只有交接失败退回本页时才回到旧行为。

**跳页面后草稿全变「待处理」？**
v0.5.4 起不会，因为回写只盖自己动过的那一条。若还遇到，先升级到 v0.5.9，并确认面板标题的版本号；同时开着多个 BOSS 标签页是正常场景。

**日志出现「沟通页认不出当前会话是这个岗位」？**
沟通页地址栏被洗掉，脚本靠导航记录里的 `jobId` / `securityId` 和右侧 `span.position-name` 判断。拿不到证据时会退成「只填不发」，你去那个标签页确认后按 `Enter`。

**岗位标题后面跟着 `[ 上海·浦东新区 ]`？**
抓取时会剥掉尾部地点括号并回填 `city`；圆括号里只有出现 `市/区/·` 才当地点，所以 `（实习）`、`（React）` 不会被误剥。旧数据重抓一次即可，不会把取消勾选冲回选中。

**岗位页取消勾选，队列里还在？**
勾选状态就是队列成员资格，取消后立即消失，未发送草稿一并丢弃。若不一致，先确认版本。

**为什么成功只看「输入框清空」？**
因为「正文里出现这句话」在没发出去时也成立。输入框清空才是发送动作真的发生了的证据。

**站点改版后失效怎么办？**
按下面「关键选择器」在真实页面（F12）核对，改对应常量。抓取逻辑不依赖具体接口参数。

**报 Issue 附什么？**
「日志」页的完整日志（面板那份 + 生成器那份）、面板标题的版本号、半自动还是全自动、从哪一步开始不对。**贴日志前请自行打码 `securityId`、`lid` 等会话参数**，它们等同凭证。

```
boss-zhipin-llm-greet.user.js   唯一的生产文件，装它就行
test/                           回归测试
  build-test.js                 切出 SCRAPER-BEGIN/END 之间的抓取代码，注入仿真 DOM
  build-ui.js                   生成 UI / 发送接力 / 详情抓取 / 列表入口 / 生成器 的仿真页面
  build-pdf.js                  生成中文 PDF 三条解析路线页面
  headless.ps1                  headless Edge 的 --dump-dom 落到文件
  run.js                        逐个套件渲染并收集断言（可按子串过滤）
```

```bash
# 需要 Node.js，以及本机已安装的 Edge 或 Chrome
node test/run.js               # 全套：34 个套件、547 条断言
node test/run.js ui-smoke      # 只跑一组（按 URL / 套件名子串过滤）
node test/run.js ui-exec       # 后台生成器 8 个 case
node test/build-ui.js          # 改过 fixture 后先重建；只有 scraper / ui-smoke / ui-exec?case=ok / pdf-main 这几条 suite 会自动 build，其它 case 复用同一批 HTML
```

套件分组：`ui-smoke`（端到端闭环 257）、`ui-exec`（生成器 8 case 73）、`sendtab`（10）、`ui-detail`（13）、`ui-hop`（7 case 54）、`listsend`（12 case 95）、`scraper`（24）、`pdf`（三个场景 21）。

测试形态：

- **fixture 必须照真实 DOM 写**。列表卡片的按钮在卡片右上角、和标题不在同一层；沟通页没有 `job_detail` 链接；发送按钮是 `div` —— 这几处都吃过「fixture 假绿、真机翻车」的亏。
- **断言盯副作用，不盯日志文本**。例如直接数 `GM_openInTab` 被调用几次、开了哪些 URL，而不是信日志那句「打开 N 个标签」。
- **闸门类代码逐条破坏验证**：多条件 AND 的每个子句都要有一个「其余条件全满足、只缺它」的场景，否则那个子句只是心理安慰。`ui-listsend` 的 `fresh-tab` / `stale-mark` / `navmark` 就是这么来的。
- **时序断言要让模拟的「慢」比生产代码的「快」更慢**。桩里回执 30ms、发送间隔 2 秒时，「发送必须逐条」的断言永远为真；把回执拖到 3 秒才验得出。
- **仿真里造不出来的场景，写进「已知限制」，不假装覆盖**。比如隐藏页定时器节流、两个生成器同一拍抢单。

**Windows headless 的三个坑**（`test/headless.ps1` 里也有注释）：

1. Edge 是 GUI 子系统程序，Node 管道和 `cmd >` 重定向收 `--dump-dom` 都是 0 字节且不报错，必须用 PowerShell `Start-Process -RedirectStandardOutput` 落文件；
2. 不要传 `--user-data-dir`，传了直接 exit 13（`Multiple targets are not supported in headless mode`）；headless 本来就是一次性临时 profile；
3. PowerShell 数组字面量里逗号比 `+` 绑得紧，`"--x=" + $v,` 会拆成两个元素 → Edge 多收一个位置参数 → 同样 exit 13。必须写成 `("--x=" + $v),`。

headless 用的是虚拟时间，真实墙钟比预算小得多；`ui-smoke` 里有几条断言要真的等满 60 秒回执超时、90 秒 JD 超时和 25 秒交接超时，所以改一条断言时优先用子串只跑相关组。

## 数据与隐私

全部数据在本机 Tampermonkey 存储里，键名如下：

| 存储键 | 内容 |
| --- | --- |
| `cfg` | 全部配置，含 **API Key 明文**（仅本机）。多模型配置也在其中的 `models` 数组里 |
| `resumeText` | 简历文本 |
| `jobs` / `details` / `drafts` | 岗位列表 / JD 详情 / 草稿与发送记录。多标签下按 id 逐条合并，不整块覆盖 |
| `stats` | 今日已发送、已生成计数，以及 `resetAt` 重置时间戳；换日归零 |
| `sendReq` / `sendRes` / `sendHop` | 跨标签发送请求、回执、跨页接力牌（TTL 60 秒，用完即清） |
| `sendClaim` | 发送请求已被哪个标签页认领，保证一个请求只执行一次 |
| `pendingDetails` | 待抓详情的岗位清单（`{url, id}`），后台标签据此认领 |
| `bgBatch` | 这一轮批量的计划与心跳（`ids, autoSend, day, tick, by, role, gen, pause, stop, respawn`）。只当天有效 |
| `bgExec` | 递给生成器标签页的交接单（`token, ts, ids, claimed, claimedAt`） |
| `bgLogBuf` / `bgLogExec` | 面板日志副本 / 生成器日志副本（各最近 200 行），两个键互不覆盖 |
| `bgSent:<岗位id>` | 「这条真的发出去了」的持久凭证；续跑时先认它，避免对同一个 HR 重发 |

清除方式：

- 油猴菜单「重置全部本地数据」：全部清空，包括 `bgSent:` 凭证（用 `GM_listValues` 按前缀扫）；
- 岗位页「清空列表」：岗位、草稿、批量计划、交接单、`bgSent:` 凭证一起扫，日志副本保留；
- 简历页「清除缓存」：只清简历；
- 日志页「重置今日计数」：清零并写 `stats.resetAt`，别的旧标签页不会把数字抬回来。

**不要把带 Key 的 `cfg` 上传到任何公开仓库。换电脑前手动备份。**

## 已知限制

- 依赖网页版 DOM，BOSS 灰度改版可能随时让某个选择器失效。v0.5.9 已按真实页面修正发送按钮，但站点仍可能再改。
- 列表卡片入口（v0.5.0）是在**照截图重写的仿真 DOM** 上验证的（12 种情形、95 条断言），尚未在已登录的真实列表页上完整实测。第一次用请先跑一条，盯着日志看它点的是不是那张卡片。
- 列表入口依赖抓取时记下的 `job.listUrl`。升级前抓的老岗位没有这个字段，第一次发送会自动退回详情页入口；回面板重抓一次即可补上。
- 「默认不勾选」只对 v0.5.1 之后新抓的岗位生效；升级前已在队列里的岗位不会被脚本替你清掉。
- 并发生成、跨标签合并、生成器、续跑主要是在仿真里验证的（v0.5.6 的并发探针在真机跑过一组）。真实服务商的并发上限、限流阈值各家不同；第一次设 2–3，看 429。
- **全自动 + 生成器**这一组合只有代码路径，没有仿真断言：`ui-exec` 的 8 个 case 和 `ui-smoke` 的相关小节都跑在半自动下。第一次试全自动时请盯：日志里的「全自动」标签、每条之间的间隔、队列行是否走到「已发送」。
- 隐藏标签页的定时器会被浏览器压慢（Chromium 最快一秒一次，久了可能一分钟一次）。生成阶段不依赖定时器，但全自动的发送间隔和回执轮询会变钝。
- 单条在飞的模型请求取消不了：`GM_xmlhttpRequest` 没有中断语义。「停止批量」会当场把计划退成没人认领，但那条回包后仍可能写出一条草稿（token 已花掉）。
- 「清空列表」而生成器正在跑时，停止信号送不进去；在飞草稿仍会落盘，下一次对账按孤儿扫掉。
- 多标签合并不是数据库事务：两个页面同一拍改同一条记录的同一字段时，仍是后写者赢。你能感知的代价最多是「某条勾选/草稿再点一次」，不会再整页消失。
- 「重置今日计数」的跨标签代价：某一页在别处按下重置之前刚好发出一条、还没落盘，那一条不再占今天额度，于是今天可能多挤一条。脚本这一侧只硬保证「已经发出去的话不会再发一遍」。
- 对账每 3 秒一次，不是即时；接管那一轮时「还剩几条」最坏落后 3 秒，落在窗口里的几条最坏会重复生成一次草稿（后写者进队列，不会两条都留）。
- 换日按 UTC（北京时间早上 8 点）翻，不是本地零点。想要零点放行，去日志页按一次「重置今日计数」。
- 少数收藏卡片没有详情页链接，这种岗位抓不到 JD，也就不会生成招呼语。
- 未验证：站点反爬在真实批量场景下的表现；非好友状态走完 `friend/add` 之后究竟跳到哪；Firefox / 移动端。
- 不会自动回复 HR 的消息，也不会替你面试。它只把第一句话说体面。

## 版本

当前 **v0.5.9**。面板标题、启动日志都会打印版本号，报 Issue 时请一并附上。

**0.5.9 — 修「最早的发送都失败了」**
真实站点的这组操作按钮是 `<div class="btn-v2 btn-sure-v2">`（同组件在会话列表搜索按钮上实测），不是 `<button>`，旧选择器只查 `button, [role=button]`，于是输入框找到了、发送按钮永远匹配不到，全线报「找到了输入框但没找到『发送』按钮」。现在候选范围覆盖 `.btn-v2` / `.btn-sure-v2` / `[class*="send"]`，文案仍精确「发送」，「提交」只认右侧面板；`clickSendButton` 先等按钮出现、再等它摘掉 `disabled`。fixture 改成真实的 `div` 写法，旧选择器会让 16 条断言变红。

**0.5.8 — 多模型配置 UI 收敛**
「多模型并行」合并进「大模型接口」fieldset，做成可折叠的 `<details>`；每个模型是一张与单模型表单同风格的卡片（label + input），删除按钮在标题里，改用事件委托（不再依赖页面全局函数），删除有确认。不再占一大块独立面板。

**0.5.7 — 多模型真正并行**
`cfg.models` 多组模型；批量按岗位 id 哈希分配，每个模型一条独立子队列，worker 共享同一个队列引用（修掉「每人拿到一份拷贝、抢同一条岗位」导致实际只有一路在飞的 bug）。新增模型迁移与防御性补齐；修 `saveCfg()` 只存单 Key 字段、导致迁移出的空 Key 模型让生成直接报错的问题。日志按模型分行，并公布每轮分配条数。

**0.5.6 — 并发实测探针**
每次模型请求记录起止时间，批量结束输出「墙上时间 / 累计时间 / 峰值同时在飞 / 实际并发度」，并按模型拆开报。真机实测：8 路确实达到峰值 8，但实际并发度 4.6，单条延迟 34–202 秒 —— 瓶颈是模型推理，不是 Key 限流；换不同模型并行比同模型多 Key 更有效。

**0.5.5 — 生成搬进后台「生成器」标签页**
「即使我离开了，语句生成也不能被打断」：生成不需要 DOM，所以循环搬到脚本自己开的常驻标签页；面板降级为观众，日志分两个键，`beforeunload` 只在执行者身上武装，普通页不再弹「是否离开网站？」；交接 25 秒没人认领退回本页跑；生成阶段零定时器。

**0.5.4 — 多标签不再互相连锅端**
`drafts` / `jobs` / `stats` / `details` / `pendingDetails` 改成「只盖自己动过的那条」+ 动手前对账；今日计数取大值并引入 `stats.resetAt`；换日真的归零。解掉「跳一次页面草稿全变待处理」「岗位 19 · 详情 12」。

**0.5.3 — 整页跳转的续跑兜底**
`bgBatch` 计划 + 心跳 + `autoResume` + `bgLogBuf` 日志副本 + `bgSent:<id>` 持久凭证。v0.5.5 之后它是主路径失败时的兜底。

**0.5.2 — 并发生成，发送仍逐条**
`genConcurrency`（默认 3，1–8）；`genBusy` 合流、`sendBusy` 互斥；429/5xx 退避加抖动。

**0.5.1 — 默认不勾选 + 单条全自动**
抓到的岗位默认不进队列，勾选才处理；勾选触发防抖批量抓 JD；全自动下单条也叫「生成并发送」，`sendOne()` 成为唯一发送实现。

**0.5.0 — 列表卡片发送入口**
默认在后台列表页点这条岗位自己的沟通按钮，一步到沟通页；走不通自动退回详情页入口；`sendClaim` 保证一个请求只执行一次。

更早：0.4.3 没 JD 一律不生成；0.4.2 修详情永远为 0（对象当 id 用）；0.4.1 跨页发送接力 + 沟通入口只点最里层 `<a>` + 会话身份双证据；0.4.0 之前的版本记录见 git 历史（若未初始化仓库，以本文件为准）。
